## 1. Purpose and authority boundary

This document defines a new **YOLO exploratory competition lane** for the AIMO Interpretability Challenge. The lane permits label-free, hand-designed competition submissions before the official training-data and CoT-activation scientific gate opens.

It does **not** open scientific execution, alter the scientific preregistration gate, or convert leaderboard outcomes into scientific evidence.

The repository therefore has three parallel lanes:

```text
PRE-GATE INFRASTRUCTURE
    engineering correctness and contract execution

YOLO EXPLORATORY COMPETITION
    frozen label-free submission batteries and external adjudication

SCIENTIFIC
    release custody -> observational audit -> preregistration -> execution
```

The governing architecture is:

```text
I || Y || S
```

There is no automatic authority transfer between the three lanes.

In particular:

```text
YOLO result != scientific result
competition performance != mechanism evidence
external acceptance != local lifecycle certification
```

The future scientific gate remains governed exclusively by the existing `RELEASE_REGISTRY.json` jurisdiction for official training data and the official CoT activation interface. Nothing in the YOLO lane may populate, reinterpret, or bypass that registry.

## 2. YOLO lane objective

The first battery, `YOLO001-B1`, asks a deliberately narrow exploratory question:

> Does a simple, label-free final-answer self-consistency heuristic show any externally adjudicated predictive signal for organizer-defined robustness?

The working relation is predictive only:

```text
self-consistency = candidate predictive correlate of organizer-defined robustness
```

No causal or mechanistic claim is licensed.

`YOLO001-B1` is an **exploratory submission battery**, not a scientific experiment. It uses:

- no official training data;
- no public development labels for parameter choice;
- no private labels;
- no activation features;
- no learned classifier;
- no leaderboard-derived tuning within the battery;
- no batch-relative normalization;
- no mechanism claim.

The first battery is designed as a frozen matrix so several simple behavioral questions can be compared without selecting a winner in advance.

## 3. Battery-level blindness and exploratory epochs

The central discipline is:

```text
many frozen exploratory submissions != adaptive leaderboard optimization
```

provided the complete battery is frozen before any `YOLO001-B1` score is observed.

`YOLO001-B1` is one exploratory epoch. Once any `B1` score has been observed, any score-informed method change belongs to a new epoch such as `YOLO001-B2`.

Therefore:

```text
B1 scores -> B2 design      ALLOWED
B1 scores -> mutate B1      FORBIDDEN
```

A later battery may be explicitly leaderboard-informed. It must not be retroactively described as blind.

## 4. Battery matrix

`YOLO001-B1` contains six self-consistency probes and two leaderboard diagnostic controls.

| ID | Role | k | Temperature schedule | Decision rule |
|---|---|---:|---|---|
| `Y001-A` | `SELF_CONSISTENCY_PROBE` | 3 | `.7,.7,.7` | all 3 extractions succeed and are identical |
| `Y001-B` | `SELF_CONSISTENCY_PROBE` | 5 | `.7,.7,.7,.7,.7` | all 5 extractions succeed and are identical |
| `Y001-C` | `SELF_CONSISTENCY_PROBE` | 5 | `.7,.7,.7,.7,.7` | at least 4 successful extractions yield the same nonempty answer |
| `Y001-D` | `SELF_CONSISTENCY_PROBE` | 3 | `.4,.4,.4` | all 3 extractions succeed and are identical |
| `Y001-E` | `SELF_CONSISTENCY_PROBE` | 3 | `1.0,1.0,1.0` | all 3 extractions succeed and are identical |
| `Y001-F` | `SELF_CONSISTENCY_PROBE` | 4 | `.4,.4,.9,.9` | all 4 extractions succeed and are identical |
| `CTRL-T` | `LEADERBOARD_DIAGNOSTIC_CONTROL` | 0 | none | always `True` |
| `CTRL-F` | `LEADERBOARD_DIAGNOSTIC_CONTROL` | 0 | none | always `False` |

The matrix creates interpretable contrasts:

```text
k:                 3 -> 5
agreement rule:    unanimity -> 4/5 supermajority
temperature:       .4 -> .7 -> 1.0
regime structure:  single regime -> cross-regime
```

No composite uncertainty score or weighted heuristic is part of `B1`.

### 4.1 Diagnostic-control ceiling

`CTRL-T` and `CTRL-F` are not scientific controls and are not members of the self-consistency family. On a fixed binary hidden set, their accuracies can expose aggregate private class balance. Therefore they are explicitly classified as `LEADERBOARD_DIAGNOSTIC_CONTROL`.

Once their scores are observed, any later use of that prevalence information is leaderboard-informed and must belong to a later exploratory epoch. It cannot enter the future scientific lane without a separately authorized design.

## 5. Shared execution contract

All six self-consistency members use one shared inference engine. Each scored ZIP is self-contained, but behavior differs only through a frozen protocol manifest rather than variant-specific implementation logic.

### 5.1 Track and model contract

```text
TRACK               Small Model Track
MODEL INPUT         organizer-supplied model_id
CODEBENCH ALIAS     qwen3-8b:low
CHECKPOINT           deepseek-ai/DeepSeek-R1-0528-Qwen3-8B
MODEL LOADS          once per are_robust(...) call
PROBLEM DEPENDENCE   per-problem only
BATCH NORMALIZATION  none
LABEL USE            none
NETWORK              none
```

The implementation must resolve the competition alias according to the pinned official starter contract. It must not introduce a different model.

### 5.2 Shared generation parameters

Unless a member's temperature schedule says otherwise:

```text
do_sample            True
top_p                0.95
top_k                0
num_beams            1
repetition_penalty   1.0
max_new_tokens       2048
use_cache            True
stop                  model/tokenizer EOS
```

Each problem is judged independently. No score, percentile, median, threshold, or other statistic may be computed across co-batched problems for prediction purposes.

### 5.3 Prompt contract

The exact organizer-supplied problem string is preserved verbatim and followed by the fixed suffix:

```text
<EXACT ORGANIZER PROBLEM STRING>

Solve the problem independently. Reason as needed.
End your response with exactly one line:
FINAL: <answer>
```

The model-facing representation uses the checkpoint's normal chat template with generation prompt enabled. The design introduces no custom system-message semantics beyond what the tokenizer/template requires.

Only the newly generated continuation is eligible for answer extraction.

## 6. Deterministic stochasticity

`B1` uses controlled stochastic sampling with replayable per-problem seeds.

### 6.1 Shared seed namespace

Paired contrasts share a seed namespace so temperature changes do not also change the selected random-stream identity.

```text
battery_id       = YOLO001-B1
seed_namespace   = YOLO001-B1
```

For problem string `X` and one-based sample index `i`:

```text
payload =
    UTF8("YOLO001-B1")
    || 0x00
    || UTF8(X)
    || 0x00
    || ASCII(i)

digest = SHA256(payload)
seed = big_endian_uint64(digest[0:8]) & 0x7fffffffffffffff
```

`X` is the exact Python string supplied by the organizer. Before hashing, there is no trimming, Unicode normalization, newline rewriting, whitespace collapsing, or other canonicalization.

Sample-index allocation is:

```text
Y001-A: 1,2,3
Y001-B: 1,2,3,4,5
Y001-C: 1,2,3,4,5
Y001-D: 1,2,3
Y001-E: 1,2,3
Y001-F: 1,2,3,4
```

The implementation must pass the derived seed through a per-sample generator or equivalent isolated RNG mechanism rather than relying on uncontrolled global RNG state across problems.

The reproducibility claim is narrow:

```text
seed-replayable under the same model/runtime conditions
```

This is not a claim of bit-identical generation across arbitrary hardware, CUDA, PyTorch, or Transformers versions.

A later protocol revision must use a new battery/seed namespace, such as `YOLO001-B2`, unless the later design explicitly declares a deliberate cross-epoch shared-stream comparison.

## 7. Answer extraction and normalization

For each generated continuation:

1. Split the continuation into lines.
2. Scan from bottom to top.
3. Select the last line whose stripped prefix begins case-insensitively with `FINAL:`.
4. Take the substring after that line's first `:`.
5. Missing or empty content is `EXTRACTION_FAILURE`.

Normalization is deliberately syntactic and conservative:

```text
Unicode NFKC
-> trim leading/trailing whitespace
-> remove one surrounding $...$ pair if the entire answer is wrapped by it
-> collapse internal whitespace runs to one ASCII space
-> remove one terminal period
```

Case is preserved.

No mathematical equivalence engine is permitted in `B1`. For example, absent literal normalized equality:

```text
1/2        != 0.5
sqrt(2)    != \sqrt{2}
x=3        != 3
```

This may undercount conceptual agreement. That conservatism is intentional because symbolic equivalence would introduce a second interpretation system and additional degrees of freedom.

## 8. Decision semantics

Let normalized extracted answers be `a_i`.

### 8.1 Unanimity members

For `Y001-A`, `Y001-B`, `Y001-D`, `Y001-E`, and `Y001-F`:

```text
robust = True
iff every required extraction succeeds
and all required normalized answers are exactly identical
```

Otherwise the prediction is `False`.

### 8.2 Supermajority member

For `Y001-C`:

```text
robust = True
iff at least four of the five slots yield successful nonempty extractions
and at least four successful normalized answers are exactly identical
```

An extraction failure consumes one of the five slots like a disagreeing answer. Four agreeing successful outputs are sufficient even if the fifth slot fails extraction.

### 8.3 Empty input

`are_robust(model_id, [])` returns `[]`.

## 9. Heuristic failure versus infrastructure failure

The implementation must preserve this boundary:

```text
heuristic failure != infrastructure failure
```

### 9.1 Heuristic observations

These are valid model observations and remain inside the classifier semantics:

```text
successful generation but missing FINAL: line
successful generation but empty extracted answer
successful generations with normalized-answer disagreement
```

They contribute disagreement or `False` according to the relevant member rule.

### 9.2 Infrastructure failures

These are not robustness observations:

```text
model-load failure
tokenizer-load failure
unexpected/unsupported model alias
CUDA OOM
generation exception
invalid model return
internal output-shape violation
```

Infrastructure failures must raise/fail the submission. They must never be silently converted to robustness `False` predictions.

A Codabench infrastructure failure may use a reserve submission to retry the identical ZIP bytes. A changed ZIP is not an identical retry.

## 10. Reserve policy

The intended first-day budget is:

```text
8 frozen B1 members + 2 reserve submission slots
```

Reserve slots are governed as follows.

### 10.1 Identical-byte retry

If Codabench reports an infrastructure-level failure, the exact same ZIP SHA-256 may be resubmitted unchanged. The retry remains the same protocol member and receives a new attempt record.

### 10.2 Pre-frozen additional reserve member

A ninth or tenth distinct protocol may consume a reserve slot only if it is fully defined and included before `B1` closure. Otherwise the reserve slot remains unused.

### 10.3 Forbidden silent repair

The following is not an identical retry:

```text
failure -> change max_new_tokens -> resubmit as same Y001 member
```

Any changed executable bytes define a new execution object and require a new explicit protocol identity/epoch.

## 11. Custody namespace

## 13. Protocol state and closure

Protocol state is independent from evaluation state.

The protocol lifecycle is:

```text
OPEN -> CLOSED
```

`B1 CLOSED` means the member set, all protocol parameters, implementation identity, and exact intended submission artifacts are fixed against score-driven change.

Critically:

```text
B1 CLOSED != B1 EVALUATED
```

The legal ordering is:

```text
protocol drafted
-> implementation verified
-> all eight intended ZIPs deterministically built
-> protocol hash + implementation identity + ZIP hashes registered
-> B1 closure commit
-> first Codabench B1 upload
-> scores/results
```

No `B1` score may be observed before the closure commit.

### 13.1 Closure predicate

Define:

```text
C_B1 = P && I && Z && H
```

where:

- `P`: protocol manifest is complete;
- `I`: implementation/tests pass;
- `Z`: all eight intended ZIPs are deterministically built;
- `H`: all eight ZIP SHA-256 digests are registered.

Only then may `protocol_state` become `CLOSED`.

A different ZIP digest is a different execution object even if the claimed change appears nonfunctional.

`rank_if_observed` is explicitly ephemeral. Rank depends on other participants and observation time and is not a stable property of the artifact.

Accuracy, coverage, and invalid-prediction counts are external adjudication observations. They remain competition results rather than scientific evidence.

## 16. Evaluation state

Evaluation state changes without reopening the protocol:

```text
protocol_state:   CLOSED
evaluation_state: UNSCORED
```

before the first upload;

```text
protocol_state:   CLOSED
evaluation_state: PARTIAL
```

while intended first-attempt outcomes are arriving; and

```text
protocol_state:   CLOSED
evaluation_state: COMPLETE
```

when every intended `B1` member has one terminal first-attempt outcome.

A terminal first-attempt outcome is one of:

```text
SCORED
INFRASTRUCTURE_FAILED
WITHDRAWN_BEFORE_UPLOAD
```

Identical-byte retries may subsequently add attempt records without reopening or mutating the protocol. Completion is operational; it does not imply all members scored successfully.

## 17. What completion does not mean

`B1 EVALUATION COMPLETE` does not mean:

```text
best heuristic identified
hypothesis supported
mechanism established
scientific evidence earned
```

The family-level exploratory reading occurs only after the battery has reached its terminal first-attempt state.

Because the public validation sets are tiny, individual score differences must not be treated as stable scientific effects. Family-level directional structure is more informative than a single highest-scoring ZIP, but even a coherent family pattern remains an exploratory competition observation unless separately tested under a scientific design.

## 18. Scientific firewall

The protocol and custody records must state the following claim ceiling or its schema-equivalent representation:

```text
SCIENTIFIC_PREREGISTRATION:            false
SCIENTIFIC_EVIDENCE_STATUS:            NONE
PUBLIC_DEVELOPMENT_LABEL_USE:          NONE
TRAINING_LABEL_USE:                    NONE
LEADERBOARD_TUNING_WITHIN_BATTERY:     NONE
MECHANISM_CLAIM:                       NONE
```

A successful YOLO result does not automatically update the scientific lane:

```text
YOLO success -/-> scientific hypothesis established
```

Likewise, future scientific release registration does not retroactively convert `B1` into a scientific experiment.

## 19. Existing infrastructure provenance remains intact

The current repository history records local baseline reproduction as `ENVIRONMENT_BLOCKED` because a compatible local model-cache/GPU environment was unavailable. That observation remains true and must not be rewritten.

A later separate observation established that the exact official Small-track baseline artifact executed on the organizer's Codabench environment with:

```text
submission_id         915072
accuracy              0.47
coverage              1.0
invalid_predictions   0
```

The correct historical representation is therefore:

```text
LOCAL BASELINE REPRODUCTION:       ENVIRONMENT_BLOCKED
EXTERNAL CODABENCH CONTRACT SMOKE: PASSED
```

These describe different execution surfaces. External smoke success does not mutate the earlier local environment result into a local pass.

This design does not authorize rewriting the existing infrastructure receipt or creating a local `CONTRACT_SMOKE_PASS` receipt.

## 20. Implementation architecture

After this written design is explicitly approved and an implementation plan is separately written and approved, implementation should follow these boundaries:

1. one shared self-consistency inference engine;
2. manifest-driven member behavior;
3. separate trivial implementations or manifest modes for `CTRL-T` and `CTRL-F`;
4. deterministic packaging using the repository's existing packaging infrastructure;
5. synthetic/test-double verification for seed derivation, extraction, normalization, decision rules, failure semantics, manifest validation, deterministic ZIPs, and custody joins;
6. no public-development-label feedback during implementation verification;
7. no score-informed code changes before `B1` closure.

The implementation must make the frozen design executable without deciding a different experiment.

## 21. Acceptance criteria for implementation planning

A later implementation plan must not begin until this design receives explicit user approval in written-spec form.

The eventual implementation may declare `B1 CLOSED` only when all of the following are true:

- the approved protocol manifest exists and validates;
- the shared inference implementation matches this design;
- seed derivation has deterministic unit tests;
- extraction and normalization have exact unit tests;
- every member decision rule has boundary-case tests;
- heuristic failures and infrastructure failures are distinguishable in tests;
- all eight intended Small-track ZIPs are built deterministically;
- every intended ZIP contains root `solution.py` and root `small.txt`;
- every ZIP has a recorded SHA-256 digest;
- the custody manifest binds protocol, implementation commit, upstream pin, and ZIP digests;
- no `B1` Codabench score has yet been observed;
- the closure commit is recorded before the first `B1` upload.

## 22. Non-goals

`YOLO001-B1` does not attempt to:

- train a robustness classifier;
- infer causal mechanisms;
- establish activation-level interpretability;
- estimate deployment prevalence;
- reproduce hidden perturbations;
- reconstruct private labels;
- optimize against the public leaderboard within `B1`;
- alter the future scientific feature ontology;
- alter `RELEASE_REGISTRY.json`;
- merge infrastructure and scientific authority;
- prove self-consistency is a valid general robustness measure.

## 23. Frozen design summary

The design freezes the following core invariants:

```text
protocol freeze != artifact build != submission != external result

paired contrast -> shared seed namespace

heuristic failure != infrastructure failure

CTRL-T/F = leaderboard diagnostic controls, not scientific controls

protocol.json = pre-score specification

protocol -> implementation -> ZIP SHA -> Codabench submission -> result

C_B1 = P && I && Z && H

B1 CLOSED != B1 EVALUATED

B1 score-informed change -> B2, never mutated B1

LOCAL ENVIRONMENT_BLOCKED and EXTERNAL CODABENCH PASS may both remain true

I || Y || S
```

The intended lifecycle is:

```text
DESIGN APPROVED
-> SPEC COMMITTED
-> IMPLEMENTATION PLAN
-> IMPLEMENTATION
-> TESTS + DETERMINISTIC BUILDS
-> PROTOCOL HASH + 8 ZIP HASHES REGISTERED
-> B1 CLOSED
-> FIRST B1 CODABENCH UPLOAD
-> RESULTS APPENDED
-> B1 EVALUATION COMPLETE
-> FAMILY-LEVEL EXPLORATORY READ
-> OPTIONAL B2
```

Until this written specification itself receives explicit approval, no implementation plan, YOLO implementation code, `B1` manifest, `B1` custody record, or `B1` submission is authorized.
