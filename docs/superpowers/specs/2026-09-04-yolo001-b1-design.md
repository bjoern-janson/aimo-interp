## 1. Purpose and authority boundary

This document defines a **YOLO exploratory competition lane** for the AIMO Interpretability Challenge. The lane permits frozen, label-free, hand-designed competition submissions before the official training-data and CoT-activation scientific gate opens.

It does **not** open scientific execution, alter the scientific preregistration gate, or convert leaderboard outcomes into scientific evidence.

The repository therefore has three parallel lanes:

```text
PRE-GATE INFRASTRUCTURE
    engineering correctness and contract execution

YOLO EXPLORATORY COMPETITION
    frozen label-free submission batteries and external adjudication

SCIENTIFIC
    release custody -> observational audit -> preregistration -> execution
```

The governing architecture is:

```text
I || Y || S
```

There is no automatic authority transfer between them:

```text
YOLO result != scientific result
competition performance != mechanism evidence
external acceptance != local lifecycle certification
```

`RELEASE_REGISTRY.json` retains sole jurisdiction over the future scientific gate artifacts. The YOLO lane may not populate, reinterpret, or bypass that registry.

## 2. YOLO001-B1 objective

`YOLO001-B1` asks one narrow exploratory question:

> Does a simple, label-free final-answer self-consistency heuristic show any externally adjudicated predictive signal for organizer-defined robustness?

The working relation is predictive only:

```text
self-consistency = candidate predictive correlate of organizer-defined robustness
```

No causal or mechanistic claim is licensed.

`YOLO001-B1` is an **exploratory submission battery**, not a scientific experiment. It uses:

- no official training data;
- no public development labels for parameter choice;
- no private labels;
- no activation features;
- no learned classifier;
- no leaderboard-derived tuning within the battery;
- no batch-relative normalization;
- no mechanism claim.

## 3. Battery-level blindness and exploratory epochs

The central discipline is:

```text
many frozen exploratory submissions != adaptive leaderboard optimization
```

provided the complete battery is frozen before any `YOLO001-B1` score is observed.

`YOLO001-B1` is one exploratory epoch. Once any `B1` score has been observed, any score-informed method change belongs to a new epoch such as `YOLO001-B2`.

```text
B1 scores -> B2 design      ALLOWED
B1 scores -> mutate B1      FORBIDDEN
```

Later batteries may be explicitly leaderboard-informed. They must not be described retroactively as blind.

## 4. Frozen B1 matrix

`YOLO001-B1` contains six self-consistency probes and two leaderboard diagnostic controls.

| ID | Role | k | Temperature schedule | Decision rule |
|---|---|---:|---|---|
| `Y001-A` | `SELF_CONSISTENCY_PROBE` | 3 | `.7,.7,.7` | all 3 extractions succeed and are identical |
| `Y001-B` | `SELF_CONSISTENCY_PROBE` | 5 | `.7,.7,.7,.7,.7` | all 5 extractions succeed and are identical |
| `Y001-C` | `SELF_CONSISTENCY_PROBE` | 5 | `.7,.7,.7,.7,.7` | at least 4 successful extractions yield the same nonempty answer |
| `Y001-D` | `SELF_CONSISTENCY_PROBE` | 3 | `.4,.4,.4` | all 3 extractions succeed and are identical |
| `Y001-E` | `SELF_CONSISTENCY_PROBE` | 3 | `1.0,1.0,1.0` | all 3 extractions succeed and are identical |
| `Y001-F` | `SELF_CONSISTENCY_PROBE` | 4 | `.4,.4,.9,.9` | all 4 extractions succeed and are identical |
| `CTRL-T` | `LEADERBOARD_DIAGNOSTIC_CONTROL` | 0 | none | always `True` |
| `CTRL-F` | `LEADERBOARD_DIAGNOSTIC_CONTROL` | 0 | none | always `False` |

The matrix exposes simple contrasts:

```text
k:                 3 -> 5
agreement rule:    unanimity -> 4/5 supermajority
temperature:       .4 -> .7 -> 1.0
regime structure:  single regime -> cross-regime
```

No composite uncertainty score or weighted heuristic is part of `B1`.

### 4.1 Diagnostic-control ceiling

`CTRL-T` and `CTRL-F` are not scientific controls and are not members of the self-consistency family. On one fixed binary hidden set, their accuracies can expose aggregate private class balance. They are therefore explicitly `LEADERBOARD_DIAGNOSTIC_CONTROL` objects.

Once their scores are observed, any later use of that prevalence information is leaderboard-informed and must belong to a later exploratory epoch. It cannot silently enter the scientific lane.

## 5. Shared execution contract

All six self-consistency members use one shared inference engine. Each scored ZIP is self-contained, but member behavior differs through frozen protocol data rather than variant-specific ad hoc code.

### 5.1 Track and model

```text
TRACK               Small Model Track
MODEL INPUT         organizer-supplied model_id
CODABENCH ALIAS     qwen3-8b:low
CHECKPOINT           deepseek-ai/DeepSeek-R1-0528-Qwen3-8B
MODEL LOADS          once per are_robust(...) call
PROBLEM DEPENDENCE   per-problem only
BATCH NORMALIZATION  none
LABEL USE            none
NETWORK              none
```

The implementation must resolve the alias according to the pinned official starter contract and must not introduce a different model.

### 5.2 Shared generation parameters

Unless a member's temperature schedule says otherwise:

```text
do_sample            True
top_p                0.95
top_k                0
num_beams            1
repetition_penalty   1.0
max_new_tokens       2048
use_cache            True
stop                  model/tokenizer EOS
```

Each problem is judged independently. No percentile, median, threshold, prevalence estimate, or other co-batch statistic may affect a prediction.

The official prediction-time budget is treated as an execution constraint, not a tunable signal:

```text
prediction_time_limit_seconds = 3600
expected_runtime_contract     = complete within the official Small-track prediction budget
```

The manifest records `generation_calls_per_problem = k` for each self-consistency member. No pre-score numeric wall-clock claim is required because runtime depends on the organizer execution surface.

### 5.3 Prompt contract

The exact organizer-supplied problem string is preserved verbatim and followed by the fixed suffix:

```text
<EXACT ORGANIZER PROBLEM STRING>

Solve the problem independently. Reason as needed.
End your response with exactly one line:
FINAL: <answer>
```

The model-facing representation uses the checkpoint's normal chat template with generation prompt enabled. The design adds no custom system-message semantics beyond what the tokenizer/template requires.

Only the newly generated continuation is eligible for answer extraction.

## 6. Deterministic stochasticity

B1 uses controlled stochastic sampling with replayable per-problem seeds.

### 6.1 Shared seed namespace

Paired contrasts share one seed namespace so temperature comparisons do not also change the selected random-stream identity.

```text
battery_id       = YOLO001-B1
seed_namespace   = YOLO001-B1
```

For exact organizer problem string `X` and one-based sample index `i`:

```text
payload =
    UTF8("YOLO001-B1")
    || 0x00
    || UTF8(X)
    || 0x00
    || ASCII(i)

digest = SHA256(payload)
seed = big_endian_uint64(digest[0:8]) & 0x7fffffffffffffff
```

Before hashing `X`, there is no trimming, Unicode normalization, newline rewriting, whitespace collapsing, or other canonicalization.

Sample indices are:

```text
Y001-A: 1,2,3
Y001-B: 1,2,3,4,5
Y001-C: 1,2,3,4,5
Y001-D: 1,2,3
Y001-E: 1,2,3
Y001-F: 1,2,3,4
```

The implementation must use a per-sample generator or equivalent isolated RNG mechanism rather than uncontrolled global RNG state across problems.

The reproducibility claim is narrow:

```text
seed-replayable under the same model/runtime conditions
```

It is not a claim of bit-identical generation across arbitrary hardware or software stacks.

A later protocol revision must use a new battery/seed namespace such as `YOLO001-B2` unless that later design explicitly declares a deliberate cross-epoch shared-stream comparison.

## 7. Answer extraction and normalization

For each generated continuation:

1. split into lines;
2. scan bottom-to-top;
3. select the last line whose stripped form begins case-insensitively with `FINAL:`;
4. take the substring after that line's first `:`;
5. missing or empty content is `EXTRACTION_FAILURE`.

Normalization is deliberately syntactic:

```text
Unicode NFKC
-> trim leading/trailing whitespace
-> remove one surrounding $...$ pair if the entire answer is wrapped by it
-> collapse internal whitespace runs to one ASCII space
-> remove one terminal period
```

Case is preserved.

No mathematical equivalence engine is permitted. For example:

```text
1/2        != 0.5
sqrt(2)    != \sqrt{2}
x=3        != 3
```

This may undercount conceptual agreement. That conservatism is intentional because symbolic equivalence would introduce a second interpretation system.

## 8. Decision semantics

For `Y001-A`, `Y001-B`, `Y001-D`, `Y001-E`, and `Y001-F`:

```text
robust = True
iff every required extraction succeeds
and all required normalized answers are exactly identical
```

Otherwise the prediction is `False`.

For `Y001-C`:

```text
robust = True
iff at least four of the five slots yield successful nonempty extractions
and at least four successful normalized answers are exactly identical
```

An extraction failure consumes one of the five slots like a disagreement. Four agreeing successful outputs are sufficient even if the fifth slot fails extraction.

`are_robust(model_id, [])` returns `[]`.

## 9. Heuristic failure versus infrastructure failure

The implementation must preserve:

```text
heuristic failure != infrastructure failure
```

Valid heuristic observations include:

```text
successful generation but missing FINAL: line
successful generation but empty extracted answer
successful generations with normalized-answer disagreement
```

They contribute disagreement or `False` according to the member rule.

Infrastructure failures include:

```text
model-load failure
tokenizer-load failure
unexpected/unsupported model alias
CUDA OOM
generation exception
invalid model return
internal output-shape violation
```

Infrastructure failures must raise/fail the submission. They must never be silently converted to robustness `False` predictions.

## 10. Reserve policy

The intended first-day budget is:

```text
8 frozen B1 members + 2 reserve submission slots
```

A reserve slot may be used for an identical-byte retry if Codabench reports an infrastructure-level failure:

```text
same ZIP SHA-256 -> new submission attempt
```

The retry remains the same protocol member.

A ninth or tenth distinct protocol may consume a reserve slot only if fully defined and included before B1 closure. Otherwise the reserve remains unused.

A changed ZIP is never an identical retry. For example:

```text
failure -> change max_new_tokens -> same member ID
```

is forbidden. Changed executable bytes require a new explicit execution object and, if score-informed, a later exploratory epoch.

## 13. Protocol state and B1 closure

Protocol state is:

```text
OPEN -> CLOSED
```

`B1 CLOSED` means the member set, parameters, implementation identity, and exact intended submission artifacts are fixed against score-driven change.

```text
B1 CLOSED != B1 EVALUATED
```

The legal ordering is:

```text
protocol drafted
-> implementation verified
-> all eight intended ZIPs deterministically built
-> protocol hash + implementation identity + ZIP hashes registered
-> closure commit
-> first Codabench B1 upload
-> results
```

No B1 score may be observed before the closure commit.

Define:

```text
C_B1 = P && I && Z && H
```

where:

- `P`: protocol manifest complete;
- `I`: implementation/tests pass;
- `Z`: all eight intended ZIPs deterministically built;
- `H`: all eight ZIP SHA-256 values registered.

Only then may `protocol_state` become `CLOSED`.

A different ZIP digest is a different execution object even if the claimed change appears nonfunctional.

## 14. Custody manifest

`yolo/batteries/YOLO001-B1.custody.json` binds the frozen protocol to executable bytes.

Schema:

```text
aimo-interp-yolo-battery-custody/v0.1
```

It records at least:

```text
schema
battery_id
protocol_sha256
protocol_git_blob_sha
implementation_commit
upstream_contract_commit
build_source_commit
track
closed_at_utc
protocol_state
artifacts
```

Each artifact record contains at least:

```text
protocol_id
zip_filename
zip_sha256
zip_size_bytes
source_directory
track
small_marker
```

The authoritative join is:

```text
protocol ID -> ZIP SHA-256 -> Codabench submission ID -> external result
```

### 14.1 Closure-commit identity

The custody manifest does **not** contain a `closure_commit` field. A Git commit cannot reliably contain its own not-yet-existing commit SHA without a self-reference problem.

Instead, the **closure commit** is defined as:

> the first Git commit whose tree contains the final `protocol_state=CLOSED` protocol manifest and the matching custody manifest with all eight registered ZIP digests.

That commit SHA is discoverable from Git history and is recorded later in each result event as `closure_commit_sha`.

### 14.2 Evaluation state is not custody state

The custody manifest is frozen at closure and therefore does **not** contain a mutable `evaluation_state` field.

Evaluation state is derived from the append-only result ledger. This preserves the approved orthogonality:

```text
protocol_state = CLOSED
while evaluation_state = UNSCORED / PARTIAL / COMPLETE
```

without mutating the frozen custody object.

## 15. Result ledger

After B1 closure, external observations are appended to:

```text
yolo/results/YOLO001-B1.results.jsonl
```

Each submission attempt records at least:

```text
schema
battery_id
protocol_id
zip_sha256
closure_commit_sha
codabench_submission_id
attempt_index
submitted_at_utc
observed_at_utc
execution_status
accuracy
coverage
invalid_predictions
rank_if_observed
leaderboard_snapshot_context

```

`rank_if_observed` is explicitly ephemeral. Rank depends on other participants and observation time; it is not a stable property of the artifact.

Accuracy, coverage, and invalid-prediction counts are external competition observations, not scientific evidence.

## 16. Evaluation-state derivation

Immediately after closure and before any B1 upload:

```text
protocol_state:   CLOSED
evaluation_state: UNSCORED
```

While intended first-attempt outcomes are arriving:

```text
protocol_state:   CLOSED
evaluation_state: PARTIAL
```

When every intended B1 member has one terminal first-attempt outcome:

```text
protocol_state:   CLOSED
evaluation_state: COMPLETE
```

A terminal first-attempt outcome is:

```text
SCORED
INFRASTRUCTURE_FAILED
WITHDRAWN_BEFORE_UPLOAD
```

Identical-byte retries may add later attempt records without reopening or mutating B1. Completion is operational; it does not imply every member scored successfully.

`B1 EVALUATION COMPLETE` does not mean:

```text
best heuristic identified
hypothesis supported
mechanism established
scientific evidence earned
```

The family-level exploratory reading occurs only after the first-attempt battery has reached its terminal state.

## 17. Scientific firewall

The protocol/custody claim ceiling must include the schema-equivalent of:

```text
SCIENTIFIC_PREREGISTRATION:            false
SCIENTIFIC_EVIDENCE_STATUS:            NONE
PUBLIC_DEVELOPMENT_LABEL_USE:          NONE
TRAINING_LABEL_USE:                    NONE
```

A successful YOLO result does not automatically update the scientific lane. Future scientific releases also do not retroactively convert B1 into a scientific experiment.


## 19. Implementation architecture

After this written design is explicitly approved and a separate implementation plan is written and approved, implementation should follow these boundaries:

1. one shared self-consistency inference engine;
2. manifest-driven member behavior;
3. trivial constant behavior for `CTRL-T` and `CTRL-F` without unnecessary model execution;
4. deterministic packaging through the repository's existing packaging infrastructure;
5. synthetic/test-double verification for seed derivation, extraction, normalization, member rules, failure semantics, manifest validation, deterministic ZIPs, and custody joins;
6. no public-development-label feedback during implementation verification;
7. no score-informed code changes before B1 closure.

The implementation makes the frozen design executable; it does not decide a different experiment.

## 20. Closure acceptance criteria

The eventual implementation may declare `B1 CLOSED` only when:

- the approved protocol manifest exists and validates;
- the shared inference implementation matches this design;
- deterministic seed tests pass;
- extraction/normalization tests pass;
- every member rule has boundary-case tests;
- heuristic and infrastructure failures are distinguishable in tests;
- all eight intended Small-track ZIPs are built deterministically;
- every ZIP contains root `solution.py` and root `small.txt`;
- every ZIP has a recorded SHA-256;
- custody binds protocol, implementation commit, upstream pin, and all ZIP digests;
- no B1 Codabench score has yet been observed;
- the closure commit exists before the first B1 upload.

## 21. Non-goals

B1 does not attempt to:

- train a robustness classifier;
- infer causal mechanisms;
- establish activation-level interpretability;
- estimate deployment prevalence;
- reproduce hidden perturbations;
- reconstruct private labels;
- optimize against the public leaderboard within B1;
- alter the future scientific feature ontology;
- alter `RELEASE_REGISTRY.json`;
- merge infrastructure and scientific authority;
- prove self-consistency is a valid general robustness measure.

## 22. Self-review record

The written-spec self-review checked for placeholders, contradictions, scope creep, and ambiguous state transitions.

Two custody contradictions in the first written draft were corrected before review handoff:

1. **Self-referential closure SHA:** the draft placed `closure_commit` inside the custody manifest. This is impossible to bind cleanly because the commit SHA does not exist until after the tree is committed. The final design defines the closure commit by Git history and records its SHA only in later result events.
2. **Mutable evaluation state inside frozen custody:** the draft placed `evaluation_state` inside the custody manifest even though evaluation changes after closure. The final design removes it from custody and derives `UNSCORED/PARTIAL/COMPLETE` from the append-only result ledger.

The self-review also corrected the `CODABENCH` spelling and made the runtime contract explicit without inventing a pre-score wall-clock estimate.

No `TODO`, `TBD`, unresolved implementation choice, score-dependent parameter, or scientific authority expansion remains in this design.

## 23. Frozen design summary

Core invariants:

```text
protocol freeze != artifact build != submission != external result

paired contrast -> shared seed namespace

heuristic failure != infrastructure failure

CTRL-T/F = leaderboard diagnostic controls, not scientific controls

protocol.json = pre-score specification

protocol -> implementation -> ZIP SHA -> Codabench submission -> result

C_B1 = P && I && Z && H

B1 CLOSED != B1 EVALUATED

B1 score-informed change -> B2, never mutated B1

LOCAL ENVIRONMENT_BLOCKED and EXTERNAL CODABENCH PASS may both remain true

I || Y || S
```

Lifecycle:

```text
WRITTEN SPEC APPROVED
-> IMPLEMENTATION PLAN
-> IMPLEMENTATION
-> TESTS + DETERMINISTIC BUILDS
-> PROTOCOL HASH + 8 ZIP HASHES REGISTERED
-> B1 CLOSURE COMMIT
-> FIRST B1 CODABENCH UPLOAD
-> RESULTS APPENDED
-> B1 EVALUATION COMPLETE
-> FAMILY-LEVEL EXPLORATORY READ
-> OPTIONAL B2
```

Until this written specification itself receives explicit approval, no implementation plan, YOLO implementation code, B1 protocol manifest, B1 custody record, or B1 submission is authorized.
